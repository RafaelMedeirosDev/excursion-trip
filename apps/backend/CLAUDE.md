# Backend — Gestão de Excursões

API NestJS + Prisma (PostgreSQL) para o sistema de gestão de excursões. Este arquivo descreve a arquitetura em camadas do backend. **A fonte de verdade detalhada de cada camada (convenções, templates, checklist) vive em `.claude/skills/{camada}/SKILL.md`** — este documento é só o mapa; consulte a skill antes de gerar código.

- **`GET /users` (primeiro `list` do projeto)**: `@Roles(Role.ADM)`, escopado por `@CurrentUser().organizationId` (mesmo padrão de todo `create`). A resposta **exclui `password` e `deletedAt`** — `UserRepository.findAll` usa `select` explícito no Prisma e o tipo `Users` em `domain/UserRepository.ts` é `Omit<User, 'password' | 'deletedAt'>`, refletindo exatamente o que o `select` retorna. `password` fica de fora porque não há motivo pra devolver hash de senha numa listagem (`POST /users` continua vazando o hash, é um problema separado, não corrigido aqui). `deletedAt` fica de fora porque a query já filtra `deletedAt: null` — expor um campo que seria sempre `null` não agrega nada. Esse é o padrão a seguir pra qualquer `list` futuro: `findAll` sempre recebe `{ organizationId }` (a skill genérica de `domain`/`service`/`controller` mostra `findAll()`/`execute()` sem parâmetro, mas esse projeto sempre escopa por organização — as skills já foram atualizadas pra refletir isso, ver seção "Arquitetura em camadas").
- **`GET /customers`**: sem `@Roles` (qualquer autenticado — mesmo padrão de `POST /customers`, diferente de `GET /users` que é `ADM`-only), escopado por `organizationId`. Resposta exclui só `deletedAt` (`Customers = Omit<Customer, 'deletedAt'>` em `domain/CustomerRepository.ts`) — `Customer` não tem campo tipo senha pra excluir, mas segue o mesmo motivo de `GET /users`: a query já filtra `deletedAt: null`, então expor o campo sempre devolveria `null`.
- **`GET /events`**: `@Roles(Role.ADM)` (mesmo padrão de `POST /events`, diferente de `GET /customers` que é aberta — evento é planejamento administrativo). Resposta exclui só `deletedAt`, mesmo padrão de `GET /customers`.
- **`Event.state` (UF, branch `feat/event-state-field`)**: campo novo, obrigatório — pedido do usuário testando a tela de Evento no frontend, não dava pra saber em qual estado o evento acontecia. Novo `enum UF` no schema (as 27 siglas). `CreateEventDTO` valida com `@IsEnum(UF)`. **Pegadinha achada na hora**: `PrismaEventRepository.findAll` usa `select` explícito (não spread automático) — esquecer de incluir `state: true` ali faria o campo sumir só na listagem, sem erro nenhum, então essa é a primeira coisa a checar sempre que um campo novo for adicionado numa entidade que já tem `list`. Migration escrita à mão (`prisma migrate dev` travou por causa de 3 linhas já existentes na tabela `Event` sem valor pra coluna nova) — backfill temporário com `DEFAULT 'SP'` seguido de `DROP DEFAULT`, mesmo padrão já usado na migration de centavos.
- **`GET /excursions`**: `@Roles(Role.ADM)` (mesmo padrão de `POST /excursions`). Diferente das três listagens anteriores: `Excursion` **não tem `deletedAt` no schema** (só `createdAt`/`updatedAt`), então não há nada a excluir — e a listagem **inclui o `Event` relacionado** (`include: { event: true }` no Prisma, decisão do usuário), o primeiro `list` do projeto a usar de fato o tipo hidratado com relation (`Excursions = Excursion & { event: Event }` em `domain/ExcursionRepository.ts`) em vez da variante `Omit<>` usada em `User`/`Customer`/`Event`. **Aceita filtro opcional por status via query param** (`?status=OPEN`, branch `feat/excursion-status-filter`) — primeiro uso de `@Query()` do projeto, um só valor por vez (não lista), validado contra `ExcursionStatus` via `ListExcursionDTO` (`src/shared/dtos/`, primeiro DTO de query em vez de body). Sem `status` na query, comportamento não muda (devolve tudo). Valor fora do enum ou campo de query não declarado no DTO dão `400` (`forbidNonWhitelisted` já cobre o segundo caso automaticamente). `ExcursionRepository.findAll` ganhou `status?: ExcursionStatus` opcional, aplicado no Prisma como `where: { organizationId, ...(status ? { status } : {}) }` — mesmo padrão condicional já usado pro filtro opcional de `userId` em `Reservation`/`Payment`. **Padrão a seguir se outro `list` precisar de filtro por query param no futuro.**
- **`GET /suppliers`**: `@Roles(Role.ADM)` (mesmo padrão de `POST /suppliers`). Resposta exclui só `deletedAt` (`Suppliers = Omit<Supplier, 'deletedAt'>`), sem relations — mesmo formato de `GET /customers`/`GET /events`.
- **`GET /vehicle-bookings`**: inicialmente `@Roles(Role.ADM)`, **desde a branch `feat/employee-vehicle-visibility` aberto pra qualquer autenticado com escopo por linha** (ver bullet dedicado abaixo — criação continua `ADM`-only). Inclui as 3 relations (`excursion`, `supplier`, `user`), decisão do usuário — segundo `list` a incluir relation, depois de `GET /excursions`. `VehicleBookings = Omit<VehicleBooking, 'deletedAt'> & { excursion: Excursion; supplier: Omit<Supplier, 'deletedAt'>; user: Omit<User, 'password' | 'deletedAt'> }` em `domain/VehicleBookingRepository.ts` — os tipos das relations são auto-contidos nesse arquivo (sem importar de outro `domain/*.ts`), mesmo padrão de isolamento por arquivo. **Atenção que se repete sempre que uma listagem inclui a relation `user`: nunca incluir `password`** (mesma regra de `GET /users`, aplicada de novo aqui via `select` aninhado no Prisma).
- **`GET /expenses`**: sem `@Roles` (qualquer autenticado, mesmo padrão de `POST /expenses`). Inclui as 3 relations (`excursion`, `vehicleBooking` — pode ser `null`, `user`), decisão do usuário. `Expenses = Omit<Expense, 'deletedAt'> & { excursion: Excursion; vehicleBooking: Omit<VehicleBooking, 'deletedAt'> | null; user: Omit<User, 'password' | 'deletedAt'> }` em `domain/ExpenseRepository.ts`. `user` exclui `password`, mesma regra de sempre; `vehicleBooking` incluído não encadeia suas próprias relations (só um nível de relation por listagem, evita aninhamento sem fim).
- **`GET /boarding-points`**: inicialmente `@Roles(Role.ADM)`, **desde a branch `feat/employee-vehicle-visibility` aberto pra qualquer autenticado, sem escopo por linha** (`BoardingPoint` não tem dono — é dado de apoio pra montar reserva, mesmo nível de abertura de `GET /customers`; criação continua `ADM`-only). Inclui a relation `vehicleBooking` (obrigatória), decisão do usuário. `BoardingPoints = Omit<BoardingPoint, 'deletedAt'> & { vehicleBooking: Omit<VehicleBooking, 'deletedAt'> }` em `domain/BoardingPointRepository.ts` — mesmo tratamento de `vehicleBooking` já usado em `GET /expenses` (exclui só `deletedAt`, não encadeia as próprias relations dele).
- **`GET /reservations` — primeiro `list` com escopo por linha, não só por organização**: sem `@Roles` (aberta a `ADM` e `EMPLOYEE`), mas `ADM` vê **todas** as reservas da organização e `EMPLOYEE` vê **só** as que ele mesmo registrou (`Reservation.userId === token.sub`). Diferente de todo `list` anterior, `ReservationRepository.findAll` recebe `{ organizationId, userId? }` — `userId` opcional, só filtra quando informado. `ListReservationService.execute({ organizationId, userId, role })` decide: `role === Role.ADM` → não passa `userId` pro `findAll` (vê tudo); qualquer outro role → passa `userId` (só o dele). O `controller` não usa `@Roles` nem `RolesGuard` pra restringir — o filtro acontece dentro do `service`, com base no `role` do token. **Esse é o padrão a seguir se outro `list` precisar de visão restrita por usuário no futuro** (`Expense` também tem `userId` de quem registrou, mas isso não foi pedido pra ele — só `Reservation` e `Payment` até agora). Inclui as 4 relations (`customer`, `vehicleBooking`, `boardingPoint` — pode ser `null` —, `user` sem `password`/`deletedAt`), mesmo padrão de exclusão de sempre. **Aceita filtro opcional por status via query param** (`?status=WAITLIST`, branch `feat/reservation-status-filter`, mesmo padrão de `?status=` já usado em `GET /excursions` — um valor por vez, `ListReservationDTO` novo). **O filtro de status se combina com o escopo por linha, nunca o substitui**: `EMPLOYEE` filtrando por status continua vendo só as próprias reservas daquele status (`where: { organizationId, ...(userId ? { userId } : {}), ...(status ? { status } : {}) }` no Prisma — os dois filtros opcionais coexistem, testado explicitamente no `.spec.ts`).
- **`GET /payments`**: mesmo padrão de escopo por linha de `GET /reservations` — `ADM` vê todos os pagamentos da organização, `EMPLOYEE` vê só os que ele mesmo registrou (`Payment.userId === token.sub`), reaproveitando exatamente a mesma estrutura (`FindAll { organizationId, userId? }`, `ListPaymentService` recebendo `role`). `Payment` **não tem `deletedAt` no schema** (só `createdAt`, mesmo caso de `Excursion`). Inclui as 2 relations (`reservation`, `user` sem `password`/`deletedAt`) — `reservation` incluída não encadeia suas próprias relations (`customer`/`vehicleBooking`/`boardingPoint` de dentro dela não vêm). **Com essa feature, as 11 entidades do schema têm `list` implementado** (só `Organization` ficou de fora, não foi pedido).
- **`GET /:id` nas 10 entidades que já têm `list`** (branch `feat/get-by-id`, todas na mesma branch/PR — mesmo padrão estrutural repetido, sem decisão de negócio nova por entidade): devolve a entidade **crua, sem relations** (mesmo formato de `create`, diferente do `list` hidratado), reaproveitando o `findById` que a maioria já tinha no `Repository` (usado internamente pra validar FK) — só `Expense` e `Payment` não tinham `findById` ainda (nada mais no projeto referenciava as duas como FK) e ganharam o método + `ExpenseNotFound`/`PaymentNotFound` (erros novos) nessa feature. Mesmo `@Roles` (ou ausência) do `GET /` de cada entidade. `@Param('id', ParseUUIDPipe)` — id malformado (não-UUID) vira `400` antes de bater no banco. **`GetReservationService`/`GetPaymentService` replicam o escopo por linha do `list`** (`EMPLOYEE` só busca por ID o que é dele — `role !== ADM && entity.userId !== userId` → mesmo `NotFound`, não `403`, pra não revelar que o registro existe) — sem essa checagem, `GET /:id` seria uma forma de contornar o escopo que o `list` já aplica (brecha identificada na revisão do plano, antes de qualquer código ser escrito). **Efeito colateral de segurança corrigido de propósito**: `UserRepository.findById` até então devolvia o `User` cru (com hash de senha) — usado só internamente (nunca exposto), mas reaproveitá-lo direto pra `GET /users/:id` vazaria o hash, revivendo o problema já corrigido em `POST /users`/`GET /users` (`feat/security-hardening`). Corrigido a mesma forma: `findById` passou a usar `select` explícito (mesmos campos do `findAll`) e retornar `Users` em vez de `User` — os 2 outros lugares que já usavam `findById` (`RefreshTokenService`, `CreateVehicleBookingService`) não quebraram, nenhum dos dois lia `.password`.
- **Ciclo de vida de status da `Reservation`** (`POST /reservations/:id/pending`, `POST /reservations/:id/confirm`, `POST /reservations/:id/cancel`) — diferente de `Excursion` (endpoint genérico `PATCH /:id/status`), aqui é **uma rota/service dedicado por transição**, decisão do usuário, porque cada uma tem regra própria de validação de pagamento. Semântica de `ReservationStatus` redefinida: `WAITLIST` (novo `@default`, estado inicial, lista de espera sem pagamento) → `PENDING` (≥50% do `agreedValue` pago, garante a vaga) → `CONFIRMED` (100% pago, vaga confirmada) → `CANCELED` (terminal). `PendingReservationService`/`ConfirmReservationService` somam os `Payment`s da reserva (`PaymentRepository.findByReservationId`, método novo — `PAYMENT` soma, `REVERSAL` subtrai) e comparam contra `agreedValue` antes de trocar o status — se não bater o percentual, lançam `ReservationInsufficientPaymentForPending`/`ReservationInsufficientPaymentForConfirm`. `/confirm` aceita `WAITLIST` **ou** `PENDING` como origem (permite pular etapa se o cliente pagar 100% de uma vez, sem precisar passar por `/pending` primeiro) — única exceção à regra de "transição estrita de 1 passo" usada em `Excursion`. `/cancel` aceita qualquer origem não-terminal, com `cancelReason` **obrigatório direto no DTO** (`@IsNotEmpty`, sem precisar da regra condicional de `Excursion` porque aqui cada transição já tem sua própria rota). Transição fora da tabela pra cada rota lança `InvalidReservationStatusTransition`. **Escopo por linha nas 3 rotas, mesmo padrão de `GET /reservations`**: `ADM` muda status de qualquer reserva da organização, `EMPLOYEE` só das que ele mesmo registrou — se tentar agir sobre reserva de outro usuário, lança `ReservationNotFound` (mesmo erro usado pra organização errada, adaptado aqui pra "outro usuário", sem revelar que o recurso existe). **Bloqueia a mudança de status se a `Excursion` da reserva já estiver `DONE`/`CANCELED`** (via `reservation.vehicleBookingId → vehicleBooking.excursionId → excursion.status`, mesmo caminho usado no gate de criação) — lança `ReservationExcursionNotAvailableForStatusChange` (nome diferente de `ReservationExcursionNotAvailable`, que é sobre *criação* de reserva, não reaproveitado por ter condição/mensagem diferente). Os 3 `service`s são self-contained, repetindo a mesma sequência de busca/validação sem util compartilhado, mesmo padrão de duplicação já usado no projeto.
- **`GET /excursions/paginated` — primeira paginação real do projeto** (branch `feat/excursions-pagination`, pedido do usuário testando a listagem de Excursões com muitos registros no frontend): rota nova, dedicada, ao lado de `GET /excursions` (que **não muda em nada** — continua devolvendo o array inteiro, sem paginação). Decisão do usuário, via `AskUserQuestion`: em vez do endpoint existente mudar de comportamento condicionalmente (com/sem `page`/`limit` na query), ficou uma rota separada só pra listagem paginada — mais simples de raciocinar, resposta sempre no mesmo formato. Motivo de `GET /excursions` continuar intocado: `useExcursions()` no frontend tem 2 consumidores que precisam da lista **completa**, não paginada (`DashboardPage` conta excursões abertas pro KPI, `CreateVehicleBookingPage` popula um `Select`) — paginar o endpoint existente quebraria os dois. `ListPaginatedExcursionDTO` (`page`/`limit` com **default na própria classe**, `page = 1`/`limit = 10`, funciona porque o `ValidationPipe` global já tem `transform: true` — quem chama a rota não precisa informar nada pra já vir paginado) + `eventName?` (filtro novo, `contains`/`insensitive` no nome do `Event` relacionado, mesmo raciocínio do `?status=` já existente). `ExcursionRepository` ganhou `findAllPaginated`/`PaginatedExcursions` (`{ data, total, page, limit }`) **ao lado** de `findAll` (não reaproveita, não altera) — implementado com `Promise.all([findMany({ skip, take }), count])` no mesmo `where`. `ListPaginatedExcursionService` é um Service próprio, não uma variante condicional de `ListExcursionService` — mesmo padrão do projeto de 1 Service por caso de uso (`Pending`/`Confirm`/`CancelReservationService` já seguem essa separação). **Atenção de ordem no `Controller`, documentada no código**: `@Get('paginated')` precisa vir **antes** de `@Get(':id')` na classe — Express/Nest casam rota por ordem de registro, e `/excursions/paginated` bateria em `:id` primeiro (tentando validar `"paginated"` como UUID, `400`) se a ordem fosse invertida. Como `ExcursionRepository` ganhou um método abstrato novo, os **11 `.spec.ts` que mockam esse repositório** (não só os de `Excursion`) precisaram do campo `findAllPaginated: jest.fn()` a mais no mock — TS exige todos os métodos abstratos presentes, mesmo em specs de entidades que só usam `findAll`/`findById`.
- **`GET /reservations/paginated` — segunda paginação do projeto, mesmo padrão de `GET /excursions/paginated`** (branch `feat/reservations-pagination`): rota nova, `GET /reservations` **não muda em nada** — dos 6 consumidores de `useReservations()`/`GET /reservations` no frontend, só `ReservationsPage` é uma listagem navegável de verdade, os outros 5 (`Dashboard`, `VehicleBookingsPage`, `CreatePaymentPage`, `PaymentsPage`, `VehicleBookingDetailsPage` via `?vehicleBookingId=`) usam a lista completa (ou completa-por-veículo) só pra cálculo agregado/lookup. `ListPaginatedReservationDTO` no mesmo molde de `ListPaginatedExcursionDTO` (`page`/`limit` com default `1`/`10` na própria classe, `eventName` novo). **Diferença chave em relação a Excursion**: `Reservation` já tinha escopo por linha (`ADM` vê tudo, `EMPLOYEE` só o que registrou **ou** é responsável pelo veículo, via `OR` no Prisma) — a rota paginada **preserva esse escopo exatamente como está** (`ListPaginatedReservationService` resolve `userId: role === ADM ? undefined : userId`, mesma regra que `ListReservationService` já aplicava). A rota paginada **não suporta `?vehicleBookingId=`** (só usado por `VehicleBookingDetailsPage`, que não pagina) — de propósito, escopo fechado no que `ReservationsPage` de fato precisa. `eventName` filtra encadeando a relação `vehicleBooking → excursion → event` (`contains`/`insensitive`, 3 saltos — mais fundo que o filtro direto de Excursion, que tem a relação `event` um nível só). **Única decisão nova em relação ao padrão de Excursion**: o `select` de `Reservation` tem ~70 linhas (4 relations com exclusão manual de `password`/`deletedAt`) — extraído pra uma constante `RESERVATION_SELECT` no topo de `PrismaReservationRepository.ts`, reaproveitada por `findAll` e `findAllPaginated`, pra não duplicar um literal grande dentro do mesmo arquivo (risco real já documentado nesse mesmo `CLAUDE.md`, ver bullet de `Event.state`: "esquecer de incluir um campo novo no `select` faz o campo sumir só na listagem, sem erro"). Isso não fere a convenção de "não compartilhar entre `Service`s" — é local a uma única classe `Repository`. `ReservationRepository` ganhou mais um método abstrato (`findAllPaginated`), então os **7 `.spec.ts` que já mockavam esse repositório** (`CreateReservationService`, `GetReservationService`, `ListReservationService`, `CancelReservationService`, `PendingReservationService`, `ConfirmReservationService`, `CreatePaymentService`) precisaram do campo a mais no mock, mesmo ajuste mecânico já visto quando `countActiveByVehicleBookingId` foi adicionado.
- **`GET /payments/paginated` — terceira paginação do projeto, mesmo padrão de Excursion/Reservation** (branch `feat/payments-pagination`): `GET /payments` **não muda em nada** — dos 4 consumidores de `usePayments()`/`GET /payments` no frontend, só `PaymentsPage` é listagem navegável; `Dashboard` (soma total arrecadado), `CreatePaymentPage` e `ReservationStatusActions` (ambos filtram por `reservationId` em memória, já que `GET /payments` nunca aceitou esse filtro) usam a lista completa. **Duas diferenças em relação às duas paginações anteriores**: (1) `Payment` não tinha nenhum filtro de campo único hoje (sem `?status=` equivalente) — o único filtro que já existia no frontend era um `Input` de busca livre comparando **cliente OU evento ao mesmo tempo**, então o DTO novo (`ListPaginatedPaymentDTO`) tem um parâmetro só (`query`), não dois, resolvido no Prisma como `OR: [{ reservation: { customer: { name: {...} } } }, { reservation: { vehicleBooking: { excursion: { event: { name: {...} } } } } }]` — 4 saltos de relação, o encadeamento mais profundo dos três. - **Refresh token implementado** (branch `feat/refresh-token`): `accessToken` agora expira em 15min (`JWT_EXPIRES_IN=15m`, era `1d`) — janela de exposição pequena se vazar. `refreshToken` é um valor aleatório opaco (`crypto.randomBytes(32)`, não é JWT), válido por `REFRESH_TOKEN_EXPIRES_IN_HOURS` (novo env var), guardado no banco só como hash SHA-256 (`RefreshToken.tokenHash` — diferente da senha, que usa `bcrypt`: o refresh token já é alta entropia/aleatório, não precisa do custo proposital do bcrypt). `POST /auth/refresh` (`{ refreshToken }` → `{ accessToken, refreshToken }` novos, mesmo rate limit de `/login`) **rotaciona a cada uso** — o token antigo é revogado (`revokedAt`) e não funciona mais, mesmo que ainda não tivesse expirado; detecta reuso indevido (se um token roubado for usado, o próximo refresh do dono legítimo falha). `POST /auth/logout` (`{ refreshToken }` → `204`, sem guard — a credencial sendo revogada é o próprio refresh token) revoga a sessão; idempotente, não lança erro se o token já não existir/já estiver revogado. **Múltiplas sessões simultâneas são permitidas** — cada login gera uma linha nova de `RefreshToken`, sem mexer nas sessões já ativas do mesmo usuário (login no celular não desconecta o notebook). Entrega do refresh token é no corpo da resposta JSON, mesmo padrão do access token — decisão explícita de não usar cookie `httpOnly` por enquanto (exigiria revisitar `credentials: false` do CORS, sem frontend ainda pra justificar).
- **Rotas protegidas** (`@UseGuards(JwtAuthGuard, RolesGuard)`, Parte 2 da skill `auth`) — só `POST /auth/login` continua público:
  - `POST /organizations`, `POST /users`, `POST /events`, `POST /excursions`, `POST /suppliers`, `POST /vehicle-bookings` e `POST /boarding-points`: `@Roles(Role.ADM)` — só admin (ações administrativas/de planejamento). `POST /organizations` não é signup público: um ADM já autenticado cria organizações novas manualmente quando precisa, não existe auto-cadastro.
  - `POST /customers`, `POST /expenses`, `POST /reservations` e `POST /payments`: sem `@Roles` — qualquer autenticado (`ADM` ou `EMPLOYEE`) pode cadastrar cliente/despesa/reserva/pagamento, é tarefa operacional do dia a dia (`Expense.userId`/`Reservation.userId`/`Payment.userId` é quem registrou — vem do token, não do body).
  - `POST /users`, `POST /customers`, `POST /events`, `POST /excursions`, `POST /suppliers`, `POST /expenses`, `POST /reservations` e `POST /payments` usam `@CurrentUser().organizationId` (do JWT), não confiam em `organizationId` vindo do body — o campo nem existe nesses DTOs. `POST /excursions`/`POST /expenses`/`POST /reservations`/`POST /payments` também usam `@CurrentUser().sub` como `userId` (quem criou). `POST /vehicle-bookings` usa `@CurrentUser().organizationId` só pra validação — `userId` vem do body (ver nota acima, é o responsável pelo veículo, não quem criou).
- **Padrão de validação de FK entre entidades da mesma organização**: quando um DTO referencia outro recurso pelo id (ex.: `Excursion.eventId`, `VehicleBooking.excursionId`/`supplierId`/`userId`, `Expense.excursionId`/`vehicleBookingId`, `BoardingPoint.vehicleBookingId`, `Reservation.customerId`/`vehicleBookingId`/`boardingPointId`, `Payment.reservationId`), o `service` busca esse recurso (`XxxRepository.findById`) e confere se `organizationId` bate com o do token — se não bater ou não existir, lança o erro `XxxNotFound` correspondente (`404`), sem revelar se o recurso existe em outra organização. Já aplicado em `Excursion.eventId` (`EventNotFound`), `VehicleBooking.excursionId`/`supplierId`/`userId` (`ExcursionNotFound`/`SupplierNotFound`/`UserNotFound`), `Expense.excursionId`/`vehicleBookingId` (`ExcursionNotFound`/`VehicleBookingNotFound`, este último só se `vehicleBookingId` for informado — é opcional), `Reservation.customerId`/`vehicleBookingId`/`boardingPointId` (`CustomerNotFound`/`VehicleBookingNotFound`/`BoardingPointNotFound`) e `Payment.reservationId` (`ReservationNotFound`, novo). `BoardingPoint.vehicleBookingId` também reaproveita `VehicleBookingNotFound`.
- **Validação de intervalo de datas** (branch `fix/date-range-validation`, bug relatado pelo usuário testando `Excursion` no frontend — nada impedia `returnDate` antes de `departureDate`): `CreateExcursionService`/`CreateEventService` rejeitam com `400` (`ExcursionInvalidDateRange`/`EventInvalidDateRange`, estendendo `InvalidStateError`, mesmo padrão de `ExcursionCancelReasonRequired`) quando `returnDate < departureDate`/`endDate < startDate` — datas **iguais** continuam válidas (viagem/evento de 1 dia). Regra generalizada pra todo par início/fim do domínio: só `Excursion` e `Event` têm esse formato (`VehicleBooking.startTime`/`returnTime` são `String?` de horário, não `DateTime`, e comparar como string quebraria viagem que atravessa a meia-noite — de propósito fora dessa regra). **Primeira correção do projeto numa branch só cobrindo backend e frontend juntos** (decisão explícita do usuário — a regra é uma coisa só, duplicada em duas camadas, não duas features): o frontend espelha a mesma checagem via `.refine()` no `zod` (`excursionSchema.ts`/`eventSchema.ts`), pro usuário ver o erro antes de bater na API.
- **Setup compartilhado já existe** (criado uma única vez, não recriar): `src/external/repositories/remote/PrismaRemoteRepository.ts` (wrapper do `PrismaClient`), `src/shared/erros/base/AlreadyExistsError.ts` (`ConflictException`), `src/shared/erros/base/UnauthorizedError.ts` (`UnauthorizedException`), `src/shared/erros/base/NotFoundError.ts` (`NotFoundException`) e `src/shared/erros/base/InvalidStateError.ts` (`BadRequestException`, criado na feature de status de `Excursion`) — reaproveitáveis por qualquer entidade. `@nestjs/config` e `@nestjs/swagger` (`^7`, não `^11` — o projeto está no Nest 10) já são dependências do projeto.
- **Endurecimento de segurança** (branch `feat/security-hardening`, 4 itens adiados desde a análise completa de 2026-07-15, atacados juntos por serem pequenos e independentes): (1) **`POST /auth/login` tem rate limit** — `@nestjs/throttler` (`ThrottlerModule.forRoot([{ ttl: 60000, limit: 5 }])` em `app.module.ts`), aplicado só na rota de login via `@UseGuards(ThrottlerGuard)` + `@Throttle({ default: { ttl: 60000, limit: 5 } })` em `AuthController` — 5 tentativas por minuto por IP, a 6ª dá `429`; nenhuma outra rota do projeto tem rate limit (já protegidas por JWT, não foi pedido). (2) **App não sobe com `JWT_SECRET` vazio ou igual ao placeholder `"change-me"` do `.env.example`** — checagem síncrona no início de `bootstrap()` em `main.ts`, antes de `NestFactory.create`, lança `Error` e encerra o processo. (3) **`POST /users` não retorna mais o hash da senha** — `UserRepository.create` (domain) mudou de `Promise<User>` pra `Promise<Users>` (reaproveita o tipo `Omit<User, 'password' | 'deletedAt'>` que já existia pro `list`), `PrismaUserRepository.create` passou a usar `select` explícito (mesmos campos do `select` já usado em `findAll`) em vez de devolver o resultado cru do Prisma — mesmo padrão de sempre, só que agora também no `create`, não só no `list`. (4) **`ValidationPipe` global ganhou `forbidNonWhitelisted: true`** (`main.ts`) — campo não declarado no DTO agora é rejeitado com `400` em vez de silenciosamente descartado.
- **CORS habilitado** (branch `feat/cors`, preparando o backend pro frontend consumir a API de outra origem): `app.enableCors({ origin: ... })` em `main.ts`, lendo a origem permitida da variável de ambiente `CORS_ORIGIN` (nova, em `.env`/`.env.example`) — aceita uma ou mais origens separadas por vírgula (`CORS_ORIGIN?.split(",").map(o => o.trim())`). Sem `credentials: true` — a API usa JWT via header `Authorization`, não cookie, então não precisa. `CORS_ORIGIN` no `.env.example` está com um valor de placeholder (`http://localhost:3001`) já que o frontend ainda não tem framework/porta escolhida — **trocar pro valor real assim que o frontend for definido** (porta de dev e, depois, domínio de produção).
- **Testes automatizados**: `jest.config.ts` na raiz do backend (`preset: ts-jest`, `moduleNameMapper` resolvendo `src/...` pros imports absolutos, regex `^src/(.*)$` — funciona em qualquer profundidade de pasta, não é um alias de nível fixo). Todos os `Create*Service`/`Get*Service`/`List*Service` (e as variações de `Reservation`) têm `.spec.ts` ao lado do arquivo testado. Cobrem só a camada `service`, com mocks manuais dos `Repository` (`jest.Mocked<XRepository>` + `jest.fn()`, sem `Test.createTestingModule()` — `Service` é classe simples, o container do Nest não entra em jogo num teste unitário desse nível). Ainda não existe teste de `Controller`, `Prisma*Repository` (precisaria de banco) nem e2e — `Test.createTestingModule()`/e2e é o próximo passo natural quando isso for necessário. Skills atualizadas pra gerar direto na pasta certa (`service`, `controller`, `tools`, `auth`).

## Arquitetura em camadas

Fluxo de uma requisição: `Controller → Service → Domain (contrato) ⟷ External (implementação)`. `Controller` nunca chama `Repository` direto — sempre passa por um `Service`. `Service` nunca importa Prisma direto — só o contrato abstrato de `domain`.

| Camada | Pasta | O que mora aqui | Skill |
|---|---|---|---|
| Controller | `src/controller/` | Endpoints HTTP, `{Entity}Controller.ts` | `.claude/skills/controller` |
| Domain | `src/domain/` | Contrato `{Entity}Repository` (classe abstrata) + tipos | `.claude/skills/domain` |
| Service | `src/service/{dominio}/` | Regra de negócio, um caso de uso por classe, `{Operation}{Entity}Service.ts` | `.claude/skills/service` |
| External | `src/external/repositories/{remote,local}/` | Implementação concreta do contrato de `domain` | `.claude/skills/external` |
| DTO | `src/shared/dtos/` | Validação de entrada (`class-validator`) | `.claude/skills/dto` |
| Erros | `src/shared/erros/{base,cases}/` | Erros de negócio tipados | `.claude/skills/erros` |
| Tools | `src/tools/` | Function-calling para IA (equivalente a Controller, mas para a IA) | `.claude/skills/tools` |
| Auth | `src/{strategies,guards,decorators}/` | Login, proteção de rota (`@UseGuards`/`@Roles`/`@CurrentUser`) | `.claude/skills/auth` |
| Validators | `src/validators/` | Validadores customizados usados pelos DTOs | — |

**Não existe módulo por entidade** (`{Entity}Module.ts`) nem pasta `module/`, e não há uma skill dedicada para isso. Ao terminar de criar Controller/Service/Domain/External/Tools de uma entidade, registre tudo diretamente em `src/app.module.ts`: adicione o Controller a `controllers`, os Services a `providers`, faça o binding `{ provide: {Entity}Repository, useClass: Prisma{Entity}Repository }`, e — se houver Tools — inclua-as em `providers` e no `useFactory` do provider `TOOLS`.

**Não existe `usecase/`** — o equivalente é `service/`.

## Convenções que atravessam todas as camadas

- Nomes de arquivo em **PascalCase**, sem kebab-case, sem sufixo com ponto (ex.: `ContactController.ts`, não `contact.controller.ts`).
- Imports usam caminho absoluto a partir de `src` (`'src/domain/ContactRepository'`), nunca relativo.
- Parâmetros de entrada são sempre desestruturados direto na assinatura (`{ campo1, campo2 }: Create`), nunca recebidos como objeto inteiro.
- Enums vêm sempre de `@prisma/client` (fonte de verdade é o `schema.prisma`) — nunca redeclare um enum à mão.
- Só implemente as operações (`create`/`list`/`findById`/`update`/`delete`) que foram de fato pedidas — não complete o CRUD especulativamente.

### `external/repositories/{remote,local}` — atenção ao significado

- **`remote/`** = implementação contra o Postgres via Prisma (`Prisma{Entity}Repository.ts`), injetando `PrismaRemoteRepository` (criado uma única vez, registrado direto em `app.module.ts`).
- **`local/`** = implementação local do mesmo contrato sem Prisma (in-memory, fixtures, cache).

## Fluxo para adicionar uma entidade nova

Ordem sugerida, aplicando a skill de cada camada:

1. `domain` — contrato `{Entity}Repository` + tipos
2. `external` — implementação Prisma (`remote/`) do contrato
3. `dto` — DTO de entrada da operação
4. `erros` — erro(s) de negócio, se a operação tiver alguma invariante
5. `service` — caso de uso, injeta o(s) `Repository` de `domain`
5.1. `{Operation}{Entity}Service.spec.ts` ao lado do `service` — mock manual do(s) `Repository` (`jest.Mocked<XRepository>`), cobrindo o caminho de sucesso e todo erro que o `service` pode lançar
6. `controller` — endpoint HTTP, injeta o(s) `Service`
7. `tools` — só se a operação precisar ser exposta para a IA
8. Registrar tudo em `app.module.ts` (controllers, providers, binding `provide`/`useClass` — ver seção acima)
9. Rodar `pnpm --filter @excursion-trip/backend build` **e** subir a aplicação — erro de DI (`UnknownDependenciesException`) só aparece em runtime, não no build
