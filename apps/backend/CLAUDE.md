# Backend — Gestão de Excursões

API NestJS + Prisma (PostgreSQL) para o sistema de gestão de excursões. Este arquivo descreve a arquitetura em camadas do backend. **A fonte de verdade detalhada de cada camada (convenções, templates, checklist) vive em `.claude/skills/{camada}/SKILL.md`** — este documento é só o mapa; consulte a skill antes de gerar código.

- **`GET /users` (primeiro `list` do projeto)**: `@Roles(Role.ADM)`, escopado por `@CurrentUser().organizationId` (mesmo padrão de todo `create`). A resposta **exclui `password` e `deletedAt`** — `UserRepository.findAll` usa `select` explícito no Prisma e o tipo `Users` em `domain/UserRepository.ts` é `Omit<User, 'password' | 'deletedAt'>`, refletindo exatamente o que o `select` retorna. `password` fica de fora porque não há motivo pra devolver hash de senha numa listagem (`POST /users` continua vazando o hash, é um problema separado, não corrigido aqui). `deletedAt` fica de fora porque a query já filtra `deletedAt: null` — expor um campo que seria sempre `null` não agrega nada. Esse é o padrão a seguir pra qualquer `list` futuro: `findAll` sempre recebe `{ organizationId }` (a skill genérica de `domain`/`service`/`controller` mostra `findAll()`/`execute()` sem parâmetro, mas esse projeto sempre escopa por organização — as skills já foram atualizadas pra refletir isso, ver seção "Arquitetura em camadas").
- **`GET /customers`**: sem `@Roles` (qualquer autenticado — mesmo padrão de `POST /customers`, diferente de `GET /users` que é `ADM`-only), escopado por `organizationId`. Resposta exclui só `deletedAt` (`Customers = Omit<Customer, 'deletedAt'>` em `domain/CustomerRepository.ts`) — `Customer` não tem campo tipo senha pra excluir, mas segue o mesmo motivo de `GET /users`: a query já filtra `deletedAt: null`, então expor o campo sempre devolveria `null`.
- **`GET /events`**: `@Roles(Role.ADM)` (mesmo padrão de `POST /events`, diferente de `GET /customers` que é aberta — evento é planejamento administrativo). Resposta exclui só `deletedAt`, mesmo padrão de `GET /customers`.
- **`GET /excursions`**: `@Roles(Role.ADM)` (mesmo padrão de `POST /excursions`). Diferente das três listagens anteriores: `Excursion` **não tem `deletedAt` no schema** (só `createdAt`/`updatedAt`), então não há nada a excluir — e a listagem **inclui o `Event` relacionado** (`include: { event: true }` no Prisma, decisão do usuário), o primeiro `list` do projeto a usar de fato o tipo hidratado com relation (`Excursions = Excursion & { event: Event }` em `domain/ExcursionRepository.ts`) em vez da variante `Omit<>` usada em `User`/`Customer`/`Event`.
- **`GET /suppliers`**: `@Roles(Role.ADM)` (mesmo padrão de `POST /suppliers`). Resposta exclui só `deletedAt` (`Suppliers = Omit<Supplier, 'deletedAt'>`), sem relations — mesmo formato de `GET /customers`/`GET /events`.
- **`GET /vehicle-bookings`**: `@Roles(Role.ADM)` (mesmo padrão de `POST /vehicle-bookings`). Inclui as 3 relations (`excursion`, `supplier`, `user`), decisão do usuário — segundo `list` a incluir relation, depois de `GET /excursions`. `VehicleBookings = Omit<VehicleBooking, 'deletedAt'> & { excursion: Excursion; supplier: Omit<Supplier, 'deletedAt'>; user: Omit<User, 'password' | 'deletedAt'> }` em `domain/VehicleBookingRepository.ts` — os tipos das relations são auto-contidos nesse arquivo (sem importar de outro `domain/*.ts`), mesmo padrão de isolamento por arquivo. **Atenção que se repete sempre que uma listagem inclui a relation `user`: nunca incluir `password`** (mesma regra de `GET /users`, aplicada de novo aqui via `select` aninhado no Prisma).
- **`GET /expenses`**: sem `@Roles` (qualquer autenticado, mesmo padrão de `POST /expenses`). Inclui as 3 relations (`excursion`, `vehicleBooking` — pode ser `null`, `user`), decisão do usuário. `Expenses = Omit<Expense, 'deletedAt'> & { excursion: Excursion; vehicleBooking: Omit<VehicleBooking, 'deletedAt'> | null; user: Omit<User, 'password' | 'deletedAt'> }` em `domain/ExpenseRepository.ts`. `user` exclui `password`, mesma regra de sempre; `vehicleBooking` incluído não encadeia suas próprias relations (só um nível de relation por listagem, evita aninhamento sem fim).
- **`GET /boarding-points`**: `@Roles(Role.ADM)` (mesmo padrão de `POST /boarding-points`). Inclui a relation `vehicleBooking` (obrigatória), decisão do usuário. `BoardingPoints = Omit<BoardingPoint, 'deletedAt'> & { vehicleBooking: Omit<VehicleBooking, 'deletedAt'> }` em `domain/BoardingPointRepository.ts` — mesmo tratamento de `vehicleBooking` já usado em `GET /expenses` (exclui só `deletedAt`, não encadeia as próprias relations dele).
- **`GET /reservations` — primeiro `list` com escopo por linha, não só por organização**: sem `@Roles` (aberta a `ADM` e `EMPLOYEE`), mas `ADM` vê **todas** as reservas da organização e `EMPLOYEE` vê **só** as que ele mesmo registrou (`Reservation.userId === token.sub`). Diferente de todo `list` anterior, `ReservationRepository.findAll` recebe `{ organizationId, userId? }` — `userId` opcional, só filtra quando informado. `ListReservationService.execute({ organizationId, userId, role })` decide: `role === Role.ADM` → não passa `userId` pro `findAll` (vê tudo); qualquer outro role → passa `userId` (só o dele). O `controller` não usa `@Roles` nem `RolesGuard` pra restringir — o filtro acontece dentro do `service`, com base no `role` do token. **Esse é o padrão a seguir se outro `list` precisar de visão restrita por usuário no futuro** (`Expense` também tem `userId` de quem registrou, mas isso não foi pedido pra ele — só `Reservation` e `Payment` até agora). Inclui as 4 relations (`customer`, `vehicleBooking`, `boardingPoint` — pode ser `null` —, `user` sem `password`/`deletedAt`), mesmo padrão de exclusão de sempre.
- **`GET /payments`**: mesmo padrão de escopo por linha de `GET /reservations` — `ADM` vê todos os pagamentos da organização, `EMPLOYEE` vê só os que ele mesmo registrou (`Payment.userId === token.sub`), reaproveitando exatamente a mesma estrutura (`FindAll { organizationId, userId? }`, `ListPaymentService` recebendo `role`). `Payment` **não tem `deletedAt` no schema** (só `createdAt`, mesmo caso de `Excursion`). Inclui as 2 relations (`reservation`, `user` sem `password`/`deletedAt`) — `reservation` incluída não encadeia suas próprias relations (`customer`/`vehicleBooking`/`boardingPoint` de dentro dela não vêm). **Com essa feature, as 11 entidades do schema têm `list` implementado** (só `Organization` ficou de fora, não foi pedido).
- **`PATCH /excursions/:id/status` — primeiro `update` do projeto**: `@Roles(Role.ADM)`. Endpoint único e genérico (não um por ação tipo `/open`/`/close`) — `UpdateExcursionStatusService` recebe `{ status, cancelReason? }` e valida a transição contra uma tabela fixa (`ALLOWED_TRANSITIONS`, declarada no próprio `service`): `PLANNING→OPEN→CLOSED→DONE` (só um passo por vez, nunca pula etapa), `CANCELED` alcançável de `PLANNING`/`OPEN`/`CLOSED` mas não de `DONE`; `DONE` e `CANCELED` são estados finais (sem transição de saída — `ALLOWED_TRANSITIONS[DONE] = []` e `[CANCELED] = []`). Transição fora da tabela lança `InvalidExcursionStatusTransition` (`400`). `Excursion` ganhou `canceledAt`/`cancelReason` no schema (mesmo padrão de `Reservation`) — `cancelReason` é **obrigatório especificamente quando o status alvo é `CANCELED`** (validado no `service`, não dá pra expressar isso só com `class-validator` no DTO; falta lança `ExcursionCancelReasonRequired`, `400`). **Primeiro uso da categoria de erro `InvalidStateError`** (`BadRequestException`/400, `src/shared/erros/base/InvalidStateError.ts`) — a skill `erros` já documentava essa categoria, só nunca tinha sido criada; os dois erros novos (`InvalidExcursionStatusTransition`, `ExcursionCancelReasonRequired`) estendem ela.
- **`CreateVehicleBookingService`/`CreateReservationService` só criam registro se a excursão estiver `PLANNING` ou `OPEN`** — `VehicleBooking` e `Reservation` só fazem sentido enquanto a excursão ainda está em planejamento ou aberta pra reserva; em `CLOSED` (lotada), `DONE` ou `CANCELED` a criação é bloqueada (`400`, `VehicleBookingExcursionNotAvailable`/`ReservationExcursionNotAvailable`, ambos estendendo `InvalidStateError`). `CreateVehicleBookingService` já buscava a `excursion` (pra validar `organizationId`), só adicionou a checagem de `status` logo em seguida. `CreateReservationService` não tem `excursionId` direto — passou a injetar `ExcursionRepository` e busca a excursão via `vehicleBooking.excursionId` (sem checar `organizationId` de novo, já garantido por integridade referencial desde a criação do `VehicleBooking`). **`Expense` não tem esse gate — fica liberado em qualquer status da excursão** (decisão explícita: `CLOSED` só significa "excursão lotada", ainda pode surgir despesa depois). Filtro de status em `GET /excursions` e transição automática por data ficam fora de escopo (feature futura separada, se pedida).
- **`select` explícito no Prisma pra excluir campos de `list`, não `omit`**: o Prisma tem uma API `omit` que seria bem mais simples (`omit: { deletedAt: true }` em vez de listar todo campo em `select`), mas ela só é GA (estável, sem flag) a partir da **Prisma 6** — nesse projeto (Prisma `5.22.x`) ela só funcionaria como preview feature (`previewFeatures = ["omitApi"]` no `generator client`, que esse projeto não tem ligado). Por isso todo `findAll` até agora usa `select` explícito com todos os campos menos os excluídos, mesmo sendo mais verboso e exigindo atualização manual se um campo novo for adicionado ao model. Reavaliar pra `omit` se o projeto migrar pra Prisma 6 algum dia.
- **Todo campo monetário é `Int` representando centavos, nunca `Decimal`** (`VehicleBooking.value`/`price`, `Reservation.agreedValue`, `Payment.value`, `Expense.value` — migration `20260716010000_monetary_fields_as_cents`). R$ 50,50 = `5050`. DTOs validam com `@IsInt()`, não `@IsNumber()` — enviar decimal (`50.50`) no body dá `400`. Formatação pra exibição (dividir por 100) é responsabilidade do frontend, não do banco/API. Motivo: `Decimal(10,2)` já era exato no Postgres (não era bug), mas `Int`/centavos elimina qualquer risco de ponto flutuante em cálculos futuros (soma de despesas, dashboard) — padrão usado por Stripe e a maioria dos processadores de pagamento.
- **`VehicleBooking.userId` NÃO é quem cria o registro** — é o `User` (`ADM` ou `EMPLOYEE`) escolhido como responsável por aquele veículo especificamente, uma decisão de negócio do ADM que faz a requisição. Por isso vem do **body** (`@IsUUID`), não de `@CurrentUser()` — diferente de todos os outros `userId`/`organizationId` do projeto, que vêm do token. Validado contra a organização do token (`UserRepository.findById` + comparação, `UserNotFound` se não bater).
- **`VehicleBooking.plate` é único por excursão, não globalmente** (`@@unique([excursionId, plate])`) — o mesmo veículo físico pode ser reaproveitado em excursões diferentes ao longo do tempo, só não pode aparecer duas vezes na mesma excursão. Como `plate` é opcional, múltiplos `VehicleBooking`s sem placa na mesma excursão são permitidos (Postgres trata `NULL` como distinto em constraint `UNIQUE`).
- **`Excursion` não tem `startTime`/`returnTime`/`price`** — foram removidos do schema de propósito (migration `20260715143605_add_organization_to_excursion_remove_time_price`) e vão pra `VehicleBooking` quando essa entidade for implementada: um veículo alugado com mais antecedência pode ter custo (e preço de assento) diferente de um alugado em cima da hora, e cada ônibus da mesma excursão pode ter horário de saída/volta diferente. `Excursion.name` é o nome da excursão como um todo (ex.: "Excursão Réveillon 2027"), **não** de um ônibus específico — o nome de cada veículo/detalhe fica em `VehicleBooking` quando implementado.
- **`BoardingPoint` não tem campo `order`** — o schema original tinha `order: Int` (sequência do ponto de embarque), mas foi removido antes de qualquer implementação (não migrado, nunca existiu em produção): não é necessário pro caso de uso atual (cliente só escolhe um ponto entre os disponíveis, não precisa de rota sequenciada) e "prenderia" a modelagem a uma ordem física que ninguém pediu ainda. Fácil adicionar de volta se virar requisito real (ex.: roteiro pro motorista). `BoardingPoint` reaproveita o erro `VehicleBookingNotFound` (já existia da feature de `Expense`) — não foi criado nenhum erro novo pra essa entidade.
- **`Reservation.excursionId` não existe no schema** — removido de propósito antes de qualquer implementação (migration `20260716150000_reservation_vehicle_booking_required`): a reserva é sempre pra um `VehicleBooking` (ônibus) específico, não pra excursão em abstrato, e como `VehicleBooking` já tem `excursionId`, manter os dois seria dado duplicado com risco de divergência. A excursão de uma reserva é sempre obtida via join (`reservation.vehicleBooking.excursionId`). `Reservation.vehicleBookingId` é **obrigatório** (deixou de ser opcional); `Reservation.boardingPointId` continua opcional (cliente pode reservar o ônibus antes de escolher o ponto de embarque). Se `boardingPointId` for informado, o `service` confere que ele pertence ao mesmo `vehicleBookingId` da reserva — senão `BoardingPointNotFound`, mesmo se o ponto existir (só é de outro veículo).
- **`Reservation` não permite o mesmo `customerId` duas vezes no mesmo `vehicleBookingId`** (`@@unique([vehicleBookingId, customerId])`) — mesmo padrão de `VehicleBooking.plate`: constraint no schema + checagem no `service` (`findByVehicleBookingAndCustomer`) lançando `ReservationAlreadyExists` (`409`) antes de criar.
- **`Payment.type` (`PAYMENT`/`REVERSAL`) é informado no body do `POST /payments`**, não fica fixo — quem chama a API decide se está registrando um pagamento ou um estorno. Ganhou `organizationId` direto no schema, mesmo padrão das últimas entidades. Sem checagem de duplicidade — múltiplos pagamentos pra mesma `Reservation` são normais (parcelas, pagamento + estorno). Diferente das outras entidades, `Payment` não tem `updatedAt`/`deletedAt` no schema, só `createdAt` (não é editável nem soft-deletável por design).
- **`User.email` é único globalmente** (não mais por organização — mudou na feature de login, migration `20260715010000_make_email_globally_unique`). `User.cpf` e `Customer.cpf` continuam únicos só por organização.
- **Login (JWT) implementado**: `POST /auth/login` (`200`, devolve `{ accessToken }`), seguindo a skill `.claude/skills/auth` Parte 1. `JwtStrategy`, `JwtAuthGuard`, `RolesGuard`, decorators `Roles`/`CurrentUser` já existem — não recriar.
- **Rotas protegidas** (`@UseGuards(JwtAuthGuard, RolesGuard)`, Parte 2 da skill `auth`) — só `POST /auth/login` continua público:
  - `POST /organizations`, `POST /users`, `POST /events`, `POST /excursions`, `POST /suppliers`, `POST /vehicle-bookings` e `POST /boarding-points`: `@Roles(Role.ADM)` — só admin (ações administrativas/de planejamento). `POST /organizations` não é signup público: um ADM já autenticado cria organizações novas manualmente quando precisa, não existe auto-cadastro.
  - `POST /customers`, `POST /expenses`, `POST /reservations` e `POST /payments`: sem `@Roles` — qualquer autenticado (`ADM` ou `EMPLOYEE`) pode cadastrar cliente/despesa/reserva/pagamento, é tarefa operacional do dia a dia (`Expense.userId`/`Reservation.userId`/`Payment.userId` é quem registrou — vem do token, não do body).
  - `POST /users`, `POST /customers`, `POST /events`, `POST /excursions`, `POST /suppliers`, `POST /expenses`, `POST /reservations` e `POST /payments` usam `@CurrentUser().organizationId` (do JWT), não confiam em `organizationId` vindo do body — o campo nem existe nesses DTOs. `POST /excursions`/`POST /expenses`/`POST /reservations`/`POST /payments` também usam `@CurrentUser().sub` como `userId` (quem criou). `POST /vehicle-bookings` usa `@CurrentUser().organizationId` só pra validação — `userId` vem do body (ver nota acima, é o responsável pelo veículo, não quem criou).
- **Padrão de validação de FK entre entidades da mesma organização**: quando um DTO referencia outro recurso pelo id (ex.: `Excursion.eventId`, `VehicleBooking.excursionId`/`supplierId`/`userId`, `Expense.excursionId`/`vehicleBookingId`, `BoardingPoint.vehicleBookingId`, `Reservation.customerId`/`vehicleBookingId`/`boardingPointId`, `Payment.reservationId`), o `service` busca esse recurso (`XxxRepository.findById`) e confere se `organizationId` bate com o do token — se não bater ou não existir, lança o erro `XxxNotFound` correspondente (`404`), sem revelar se o recurso existe em outra organização. Já aplicado em `Excursion.eventId` (`EventNotFound`), `VehicleBooking.excursionId`/`supplierId`/`userId` (`ExcursionNotFound`/`SupplierNotFound`/`UserNotFound`), `Expense.excursionId`/`vehicleBookingId` (`ExcursionNotFound`/`VehicleBookingNotFound`, este último só se `vehicleBookingId` for informado — é opcional), `Reservation.customerId`/`vehicleBookingId`/`boardingPointId` (`CustomerNotFound`/`VehicleBookingNotFound`/`BoardingPointNotFound`) e `Payment.reservationId` (`ReservationNotFound`, novo). `BoardingPoint.vehicleBookingId` também reaproveita `VehicleBookingNotFound`.
- **Setup compartilhado já existe** (criado uma única vez, não recriar): `src/external/repositories/remote/PrismaRemoteRepository.ts` (wrapper do `PrismaClient`), `src/shared/erros/base/AlreadyExistsError.ts` (`ConflictException`), `src/shared/erros/base/UnauthorizedError.ts` (`UnauthorizedException`), `src/shared/erros/base/NotFoundError.ts` (`NotFoundException`) e `src/shared/erros/base/InvalidStateError.ts` (`BadRequestException`, criado na feature de status de `Excursion`) — reaproveitáveis por qualquer entidade. `@nestjs/config` e `@nestjs/swagger` (`^7`, não `^11` — o projeto está no Nest 10) já são dependências do projeto.
- **Nota de segurança conhecida:** `POST /users` retorna o model `User` completo, incluindo o hash da senha no campo `password` — decisão explícita do usuário pra seguir o padrão genérico das skills por enquanto (pode ser revisitado depois, ex.: omitir `password` da resposta).

## Arquitetura em camadas

Fluxo de uma requisição: `Controller → Service → Domain (contrato) ⟷ External (implementação)`. `Controller` nunca chama `Repository` direto — sempre passa por um `Service`. `Service` nunca importa Prisma direto — só o contrato abstrato de `domain`.

| Camada | Pasta | O que mora aqui | Skill |
|---|---|---|---|
| Controller | `src/controller/` | Endpoints HTTP, `{Entity}Controller.ts` | `.claude/skills/controller` |
| Domain | `src/domain/` | Contrato `{Entity}Repository` (classe abstrata) + tipos | `.claude/skills/domain` |
| Service | `src/service/` | Regra de negócio, um caso de uso por classe, `{Operation}{Entity}Service.ts` | `.claude/skills/service` |
| External | `src/external/repositories/{remote,local}/` | Implementação concreta do contrato de `domain` | `.claude/skills/external` |
| DTO | `src/shared/dtos/` | Validação de entrada (`class-validator`) | `.claude/skills/dto` |
| Erros | `src/shared/erros/{base,cases}/` | Erros de negócio tipados | `.claude/skills/erros` |
| Tools | `src/tools/` | Function-calling para IA (equivalente a Controller, mas para a IA) | `.claude/skills/tools` |
| Auth | `src/{strategies,guards,decorators}/` | Login, proteção de rota (`@UseGuards`/`@Roles`/`@CurrentUser`) | `.claude/skills/auth` |
| Validators | `src/validators/` | Validadores customizados usados pelos DTOs | — |

**Não existe módulo por entidade** (`{Entity}Module.ts`) nem pasta `module/`, e não há uma skill dedicada para isso. Ao terminar de criar Controller/Service/Domain/External/Tools de uma entidade, registre tudo diretamente em `src/app.module.ts`: adicione o Controller a `controllers`, os Services a `providers`, faça o binding `{ provide: {Entity}Repository, useClass: Prisma{Entity}Repository }`, e — se houver Tools — inclua-as em `providers` e no `useFactory` do provider `TOOLS`.

**Não existe `usecase/`** — o equivalente é `service/`.

## Convenções que atravessam todas as camadas

- Nomes de arquivo em **PascalCase**, sem kebab-case, sem sufixo com ponto (ex.: `ContactController.ts`, não `contact.controller.ts`).
- Imports usam caminho absoluto a partir de `src` (`'src/domain/ContactRepository'`), nunca relativo.
- Parâmetros de entrada são sempre desestruturados direto na assinatura (`{ campo1, campo2 }: Create`), nunca recebidos como objeto inteiro.
- Enums vêm sempre de `@prisma/client` (fonte de verdade é o `schema.prisma`) — nunca redeclare um enum à mão.
- Só implemente as operações (`create`/`list`/`findById`/`update`/`delete`) que foram de fato pedidas — não complete o CRUD especulativamente.

### `external/repositories/{remote,local}` — atenção ao significado

- **`remote/`** = implementação contra o Postgres via Prisma (`Prisma{Entity}Repository.ts`), injetando `PrismaRemoteRepository` (criado uma única vez, registrado direto em `app.module.ts`).
- **`local/`** = implementação local do mesmo contrato sem Prisma (in-memory, fixtures, cache).

## Fluxo para adicionar uma entidade nova

Ordem sugerida, aplicando a skill de cada camada:

1. `domain` — contrato `{Entity}Repository` + tipos
2. `external` — implementação Prisma (`remote/`) do contrato
3. `dto` — DTO de entrada da operação
4. `erros` — erro(s) de negócio, se a operação tiver alguma invariante
5. `service` — caso de uso, injeta o(s) `Repository` de `domain`
5.1. `{Operation}{Entity}Service.spec.ts` ao lado do `service` — mock manual do(s) `Repository` (`jest.Mocked<XRepository>`), cobrindo o caminho de sucesso e todo erro que o `service` pode lançar
6. `controller` — endpoint HTTP, injeta o(s) `Service`
7. `tools` — só se a operação precisar ser exposta para a IA
8. Registrar tudo em `app.module.ts` (controllers, providers, binding `provide`/`useClass` — ver seção acima)
9. Rodar `pnpm --filter @excursion-trip/backend build` **e** subir a aplicação — erro de DI (`UnknownDependenciesException`) só aparece em runtime, não no build

## Comandos

```bash
pnpm --filter @excursion-trip/backend dev      # nest start --watch
pnpm --filter @excursion-trip/backend build
pnpm --filter @excursion-trip/backend lint
pnpm --filter @excursion-trip/backend test      # jest, roda os .spec.ts de src/service/
pnpm --filter @excursion-trip/backend test:watch
pnpm --filter @excursion-trip/backend exec prisma migrate dev   # nova migration após mudar o schema
```
